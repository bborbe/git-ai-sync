## Summary

- Today twelve `git-ai-sync watch` processes — one per vault, one launchd agent each — hold ~328 MB of RSS between them, because every vault pays for its own interpreter and its own eager `claude_code_sdk` import
- This change adds one Go process that serves all twelve vaults, and one launchd agent that replaces the twelve
- The vault set, interval, strategy, commit prefix, pushgateway credentials and notifier settings move into one config file; nothing is duplicated across plists
- `install`, `uninstall` and `status` join `supervise` as the lifecycle surface, and they reproduce the whole setup from that one file
- The existing per-repo `watch` / `sync` / `resolve` commands keep working unchanged and without a config file, so the Python tool and the Go binary can coexist until the cutover lands

## Problem

The Python tool was written for one repository. Twelve vaults therefore mean twelve interpreters, twelve launchd agents, twelve plists to keep in sync by hand, and ten copies of the same three pushgateway credentials in world-readable plists (launchd baseline rule 10). Every settings change is a twelve-place edit, and the twelve plists have already drifted: ten run a shim with three environment variables, while `personal` and `seibert-personal` run the tool binary directly with an empty `EnvironmentVariables` dict.

The Go binary already has the sync loop (`v0.16.0`) and conflict resolution (`v0.17.0`), but it is still a single-repository command. It has no config file — `internal/config` resolves flags, then environment, then defaults — no supervisor, no metrics, no notifier, and no launchd lifecycle verbs. Until those exist there is nothing to cut over to.

## Goal

One `git-ai-sync supervise` process reads one config file, runs one sync loop per configured vault, records a per-vault metrics heartbeat and last-success, posts exactly one attention-board card when a vault fails N consecutive cycles and closes it when that vault recovers, and logs every successful push with the vault path and the pushed commit's sha. One `com.github.bborbe.git-ai-sync` launchd agent runs it. `install`, `uninstall` and `status` are the only lifecycle verbs besides `supervise`, and `status` reports what the config file names and how fresh the last metrics push is.

## Non-goals

- Retiring the Python tool. It stays installed and on `PATH` until its own retirement task runs.
- Migrating the twelve live agents. This change ships the binary and its commands; the cutover itself is an operator step in a separate task.
- Changing which vaults are watched, the sync cadence, or the conflict-resolution contract.
- Linux systemd packaging. `docs/systemd-user-service.md` stays accurate for the Python tool; the Go supervisor's systemd story is a separate change.
- A GUI, a TUI, or per-vault alert routing.
- Adding a `--config` flag or a config-file read to `watch`, `sync` or `resolve`. Those three keep today's flags → environment → defaults resolution and keep working on a machine with no config file at all.
- Any change to the Python source under `src/`, the Python tests under `tests/`, `pyproject.toml` or `uv.lock`.

## Assumptions

- The operator runs macOS with a GUI login domain, so `launchctl bootstrap gui/<uid>` works. `docs/launchd-service.md` documents the SSH/sandbox fallback, and `install` prints the same `bootstrap` command when it fails.
- A pushgateway and an attention store exist and are reachable from the operator's machine. Ten of the twelve vaults are already configured for both; the credentials move into the config file, which is `0600`.
- The supervisor shells out to `git` and to `attention-ask.py`, so the installed agent needs an explicit `PATH` (launchd baseline rule 5) and an absolute script path in config.
- `$HOME` is the only directory component the default paths derive from, so tests can point every path at a temporary directory by setting `HOME`.

## Acceptance Criteria

- [ ] A config file supplies the vault set and the shared settings, and flags beat the file which beats the environment which beats the defaults — probe: a Go test loads a config file naming two vaults with `interval: 45` and `strategy: rebase`, then runs `Load` three ways: with the file only (`Interval` is 45 s, `Strategy` is `rebase`, both vaults present); with the file plus `GIT_AI_SYNC_INTERVAL=99` and `GIT_AI_SYNC_STRATEGY=merge` (`Interval` is still 45 s and `Strategy` is still `rebase` — the file wins over the environment, asserted on both a numeric and a string field); and with the file plus an explicit `--interval 7` flag (`Interval` is 7 s). A loader that lets the environment override the file on either field fails this.
- [ ] The four config-requiring subcommands need a config file; the three sync verbs do not — probe: `status`, `install`, `uninstall` and `supervise` each run with `HOME` pointed at a temporary directory and no config file present, and each exits non-zero with stderr naming `$HOME/.config/git-ai-sync/config.yaml`; in the same temporary `HOME`, `git-ai-sync sync <throwaway-repo>` exits 0 and pushes, with no config file anywhere. A command that starts with zero vaults, or a `sync` that now demands a config file, fails this.
- [ ] `supervise` runs one loop per configured vault concurrently, and a slow vault does not stall the others — probe: a Go test starts `supervise` over two throwaway repositories with a 1 s interval, waits for a cycle on each, then cancels the context; both repositories receive a commit and a push, the run log carries one `push path=<repo> sha=` line per repository, and the call returns within 5 s with no goroutine still running (a wait group the test can observe reports zero). Second run: vault A's remote is replaced by a local remote wrapped so that its push blocks for 3 s, and vault B's cycle must still complete and log its `push path=` line within 1 s of the cycle starting. A sequential `for` loop over vaults fails the second clause.
- [ ] The push log line names the commit that reached the remote — probe: after the run above, for each repository the `sha=` in its `push path=` line equals `git -C <bare-remote> rev-parse refs/heads/<branch>`, and the subject of that commit starts with the configured commit prefix. A line logging `git rev-parse HEAD` at log time passes only when nothing else commits in between, so the test also commits to the worktree between the push and the assertion and requires the logged sha to keep naming the pushed commit.
- [ ] Metrics are pushed with `POST`, and the heartbeat does not erase the last-success series — probe: a stub HTTP server records every request; after two cycles the server has received `POST` requests carrying both `git_ai_sync_heartbeat_timestamp` and `git_ai_sync_last_success_timestamp` for each vault, and **zero** `PUT` requests. A `PUT` fails this: the pushgateway replaces the whole grouping-key group, so a `PUT` heartbeat erases last-success every cycle and the stall alert can never fire.
- [ ] N consecutive failed cycles post exactly one card, and the next success closes it — probe: with `stall_threshold: 2` and a repository whose remote has been made unreachable, a stub `attention-ask.py` on `PATH` records its argv and prints `ITEM_ID: <32-hex>`; the run posts exactly once, on the second failed cycle; the recorded argv carries `--dedup-key git-ai-sync-<label>-stalled`, `--producer-id git-ai-sync-<label>`, `--producer-kind cron`, exactly two `--option` values with `--recommend` naming one of them, a `--payload` naming the count 2, and a `--context` naming the repository path; and a subsequent successful cycle sends exactly one `POST {store}/api/1.0/attention/<id>/close` to a recording stub store. Two posts, a post on the first failure, or a missing `--producer-id` fails this.
- [ ] A missing notifier script disables the notifier instead of failing the cycle — probe: with the configured script path pointing at a non-existent file, a run over three failing cycles logs exactly one startup warning naming that path, makes zero notifier invocations, and the state file records `consecutive_failures: 3` for that vault after the third cycle. A cycle that aborts because the notifier is absent fails this.
- [ ] A hanging notifier script is bounded and does not stall the loop — probe: a stub `attention-ask.py` that sleeps 10 s; with `stall_threshold: 2`, the cycle that would post returns within 7 s, logs a WARNING naming the timeout, makes exactly one invocation (no retry within the cycle), and the next cycle still runs. An unbounded call fails this by exceeding the 7 s bound.
- [ ] A vault whose loop fails does not take the process down or stop the others — probe: three vaults, one of them a path that is a regular file rather than a repository; the run logs a failure naming that path on every cycle, the other two vaults keep pushing (`push path=` lines continue across at least two cycles), the process is still alive after 3 s, and the failing vault's loop is re-entered (its failure line count grows by one per interval rather than appearing once).
- [ ] `install` writes one baseline-compliant plist and loads it — probe: a Go test runs `install` with `HOME` in a temporary directory and a stub `launchctl` on `PATH` that records its argv; the written `~/Library/LaunchAgents/com.github.bborbe.git-ai-sync.plist` carries label `com.github.bborbe.git-ai-sync`, `ProgramArguments` whose first element is the running executable's symlink-resolved absolute path and whose remainder is `supervise --config <resolved config path>`, `KeepAlive` true, `RunAtLoad` true, `ThrottleInterval` 30, `ProcessType` `Standard`, `SoftResourceLimits` `NumberOfFiles` 4096, `HardResourceLimits` `NumberOfFiles` 8192, an `EnvironmentVariables` `PATH`, and `StandardOutPath`/`StandardErrorPath` both `/…/Library/Logs/git-ai-sync/git-ai-sync.log` under the test `HOME`; it carries **no** `NumberOfProcesses` key and **no** pushgateway password value; the log directory exists; and the stub recorded `bootout` before `bootstrap` and recorded no `kickstart`.
- [ ] `install` is idempotent and `uninstall` is complete — probe: running `install` twice produces a byte-identical plist and exits 0 both times; `uninstall` removes the plist and records one `bootout`; `uninstall` on a machine with no plist exits 0 and records no `bootout`. A second `install` that rewrites a different plist, or an `uninstall` that errors when there is nothing to remove, fails this.
- [ ] `status` reports the configured vaults, the last metrics push, and whether the agent is loaded — probe: with a config naming two vaults, a state file recording a metrics push 10 s ago, and a stub `launchctl` whose `print` exits 0, `status` prints both vault paths, prints a `last metrics push` line whose age is under 60 s, and exits 0; after the config gains a third vault and drops one, `status` prints the new set and neither of the old ones; with the state file absent it prints `never` rather than an error; and with the same stub `launchctl` configured to make `print` exit non-zero, `status` exits non-zero and names the unloaded agent.
- [ ] The config file's credentials never reach a log, the plist, or the state file — probe: with a distinctive password value in the config, a full `install` plus two `supervise` cycles leave `grep -R -c '<value>' <tmp-home>/Library <tmp-home>/.local/state` at 0 and the captured stdout/stderr containing it 0 times. The config file itself is excluded from the probe because it is the one file that legitimately holds the value; a loader that logs its own contents fails this.
- [ ] `install` refuses a config file other users can read — probe: with the config file at mode `0644`, `install` exits non-zero and names the permission problem; at `0600` it proceeds. A silent acceptance fails this, because the file holds the pushgateway password that the plist deliberately does not.
- [ ] A malformed or unknown config key is an error, not a silently ignored line — probe: a config file with an unknown top-level key, and a second one with `interval: not-a-number`, each make `Load` return a non-nil error naming the file; `supervise` with each exits non-zero, writes no state file, and logs no `push path=` line. A loader that ignores unknown keys fails this.
- [ ] `docs/launchd-service.md` describes the Go path and no longer the superseded one — probe: `grep -c 'kickstart -k' docs/launchd-service.md` returns 0, `grep -c 'NumberOfFiles' docs/launchd-service.md` matches no `1024`, `grep -c '/tmp/git-ai-sync' docs/launchd-service.md` returns 0, and `grep -c 'git-ai-sync supervise' docs/launchd-service.md` is at least 1. A doc left untouched fails this.

### Operator-executable (runs on the host after merge, before the cutover)

- Place the binary following launchd baseline rule 7, because replacing a signed binary in place is what broke code signing before the 2026-10-17 kernel panic: `CGO_ENABLED=0 go build -o ./git-ai-sync.new ./cmd/git-ai-sync` at the merged `origin/master` revision, then `codesign -f -s - ./git-ai-sync.new`, then `codesign --verify --strict ./git-ai-sync.new`, then `sudo install -m 0755 ./git-ai-sync.new /usr/local/bin/git-ai-sync` (a `mv` over the target is what `install -m 0755` performs). `/usr/local/bin` is root-owned and `sudo -n` fails, so this step is the operator's, not the container's. Record `git-ai-sync --version` output.
- Write the real config at `~/.config/git-ai-sync/config.yaml` with mode `0600`, carrying the twelve vault paths and the pushgateway credentials copied from the ten legacy plists that carry them. Never paste a credential value into a vault file or a task page.
- `/usr/local/bin/git-ai-sync install` — expect exit 0 and `launchctl print gui/$(id -u)/com.github.bborbe.git-ai-sync` reporting `state = running`. **Not** `launchctl list | grep -c git-ai-sync`: the twelve legacy labels share the `com.github.bborbe.git-ai-sync-` prefix, so that count is 13 until the cutover task removes them.
- `tail -1 ~/Library/Logs/git-ai-sync/git-ai-sync.log` shows the supervisor's start line naming twelve vaults.

## Desired Behavior

1. `internal/config` gains a YAML config file. For `supervise`, `install`, `uninstall` and `status`, `Load` resolves in this order: explicit flags, then the config file, then the environment, then the built-in defaults. The default path is `$HOME/.config/git-ai-sync/config.yaml`; those four subcommands accept `--config` to override it. A missing or unreadable file is an error naming the resolved path — never an empty vault set. `watch`, `sync` and `resolve` keep today's resolution exactly — flags, then environment, then defaults — and never read the config file.
2. The config file carries `vaults` (absolute paths), `interval`, `max_wait`, `strategy`, `commit_prefix`, `log_level`, `stall_threshold`, `attention_script`, `attention_store_url`, `state_file`, and a `pushgateway` block with `url`, `username`, `password`. `state_file` defaults to `$HOME/.local/state/git-ai-sync/status.json`. `log_level` and `max_wait` keep their existing `LOG_LEVEL` / `GIT_AI_SYNC_MAX_WAIT` semantics, now also readable from the file. Unknown keys and malformed values are errors naming the file. The file is read at mode `0600`; a group- or world-readable file is refused by `install` with a message naming the permission.
3. `supervise` starts one goroutine per configured vault, each running the existing watch loop against its own repository, and shuts them all down when the context is cancelled or a signal arrives. A panic in one vault's loop is recovered and logged; a non-cancellation return from the loop (a missing path, a conflict) is logged and the loop restarted after one interval. Neither takes the process down, and neither delays the other vaults.
4. On every cycle in which the sync pushed, the supervisor logs one INFO line `push path=<absolute vault path> sha=<commit sha>`, where the sha is the commit that was pushed — not whatever `HEAD` is when the line is written.
5. Every cycle pushes a metrics heartbeat to the configured pushgateway with `POST`, carrying `git_ai_sync_heartbeat_timestamp` and `git_ai_sync_last_success_timestamp` for that vault's label, and records the outcome in the state file for `status` to read. One writer owns the state file — the supervisor serialises the twelve loops' updates through a single collector rather than letting each loop rewrite the file — and the state directory is created at startup. `POST` is not an implementation preference: the pushgateway's `PUT` replaces the entire grouping-key group, so a `PUT` heartbeat erases last-success every cycle and the stall alert can never fire.
6. The supervisor counts consecutive failed cycles per vault. At the configured threshold (default 10, minimum 2) it posts exactly one card through `attention-ask.py` with dedup key `git-ai-sync-<label>-stalled`, and on the next successful cycle it closes that card with one `POST {store}/api/1.0/attention/<item_id>/close`. `<label>` is the vault directory's last path component, lowercased, with each run of non-alphanumeric characters collapsed to one hyphen and leading/trailing hyphens stripped — the derivation `docs/launchd-service.md` already documents and `metrics.py` already implements. The supervisor exports `ATTENTION_STORE_URL` into the child's environment from the same config value it closes against, so a post and its close can never disagree about which store they address. A missing or failing script is a startup warning and a disabled notifier, never a failed cycle.
7. `install` creates `~/Library/Logs/git-ai-sync/`, writes `~/Library/LaunchAgents/com.github.bborbe.git-ai-sync.plist`, and loads it with `bootout` then `bootstrap` (never `kickstart -k`, which re-runs the cached plist). The plist meets launchd baseline rules 1, 2, 3, 4, 5, 6 and 10, and carries `KeepAlive` and `RunAtLoad` so the supervisor comes back after a crash or a reboot. Re-running `install` rewrites a byte-identical plist and exits 0.
8. `uninstall` boots the job out and deletes the plist; on a machine with neither it exits 0. `status` prints the configured vault paths, the age of the last metrics push from the state file (reported as fresh under 60 s), and whether the agent is loaded; it exits non-zero when the agent is not loaded, so a scripted check can gate on it.

## Constraints

- New package `internal/supervise` for the multi-repo loop, and `internal/launchd` for the plist renderer and the `launchctl` calls. `internal/config` gains the file loader. Neither new package may import `internal/cli`; the CLI wires them.
- `internal/watch` keeps its current signature and behaviour. `supervise` calls it per vault rather than reimplementing the loop, so the quiet-window, conflict and lock behaviour is identical to today's.
- `go.mod` gains a YAML decoder (`gopkg.in/yaml.v3`); the repo has none today. Hand-rolling a parser to avoid the dependency is not acceptable — unknown keys must be rejected, and a real decoder gives that without bespoke code.
- The `launchctl` invocation and the `~/Library/LaunchAgents` directory are injectable, so `install`/`uninstall` are testable without touching the real launchd domain or the real `~/Library/LaunchAgents`.
- `ProgramArguments[0]` is the running executable's absolute path with symlinks resolved, so an `install` invoked through a symlink still writes the real binary path.
- **Launchd baseline, expanded here so the numbers are not a lookup into a vault page.** Rule 1: `ThrottleInterval` 30 — launchd's default of 10 s still allows about six crash-relaunches per minute. Rule 2: `SoftResourceLimits` `NumberOfFiles` 4096, `HardResourceLimits` `NumberOfFiles` 8192. Rule 3: never set `NumberOfProcesses` — it counts per user and breaks every spawn. Rule 4: `ProcessType` `Standard`, the value for a long-running daemon. Rule 5: an explicit `PATH` in `EnvironmentVariables`, because launchd's default `PATH` does not include `/usr/local/bin`. Rule 6: logs under `~/Library/Logs/git-ai-sync/`, never `/tmp`, which is wiped at reboot. Rule 10: no secret in `EnvironmentVariables` — plists are world-readable.
- `ResidentSetSize` limits are deliberately **not** carried over from the Python plists. The goal is a supervisor whose own RSS stays under 100 MB, and a hard cap would `SIGKILL` a legitimate large-vault sync rather than report it; the metrics heartbeat and the stall alert are the leak signal instead.
- The plist must not carry the pushgateway credentials or any other secret in `EnvironmentVariables`. It carries only `PATH`. Everything else comes from the config file.
- `StandardOutPath` and `StandardErrorPath` are `~/Library/Logs/git-ai-sync/git-ai-sync.log`. `install` creates the directory first; launchd does not. The state directory `~/.local/state/git-ai-sync/` is created by `supervise` at startup for the same reason.
- The supervisor's `ProgramArguments` are the absolute binary path followed by `supervise --config <resolved config path>`. That is a property of the rendered plist, not a post-merge process observation: the twelve legacy watchers still match `git-ai-sync watch` until the cutover task removes them.
- Metrics are `POST`ed, never `PUT`. The notifier is best-effort with a 5 s bound on both the post and the close: a missing script, a non-zero exit, a timeout or an unreachable store is logged at WARNING and never changes a cycle's outcome. The card contract itself — flags, `ITEM_ID:` stdout shape, the 409-on-close rule, liveness and dedup — is `docs/attention-store.md`; do not re-derive it.
- Secrets are never logged, never written into a vault file, never placed in the state file, and never echoed by `status`. The config loader must not log its own contents, at any level.
- `docs/launchd-service.md` is updated in the same change: it documents `setup-launchd` / `remove-launchd`, `/tmp` logs, `NumberOfFiles` 1024, credentials in `EnvironmentVariables`, and a `kickstart -k` fallback — all superseded for the Go path. `docs/systemd-user-service.md` is left alone.
- New code uses `github.com/bborbe/errors` for wrapping, per the repo's style: no `fmt.Errorf` and no bare `return err` in new code. Existing packages are not rewritten.
- Add a `CHANGELOG.md` bullet under `## Unreleased`.
- Nothing may touch `.github/workflows/` — the CI GitHub App holds no `workflows` permission and any commit under `.github/` is rejected at push.
- The Python source under `src/`, the Python tests under `tests/`, `pyproject.toml` and `uv.lock` must not change.

## Security / Abuse Cases

The config file holds a pushgateway password. It is read at mode `0600`, refused otherwise by `install`, never logged, never placed in the plist or the state file, and never printed by `status`. The `attention-ask.py` invocation is an argument vector, never a shell string, so a vault path containing spaces or shell metacharacters cannot become a command. The supervisor reads only the vault paths the config names; it does not walk the filesystem looking for repositories. The `--config` flag takes a path the operator supplies, and the loader refuses a file it cannot read rather than continuing with defaults.

Rationale: prompt 1 establishes the config contract every later prompt reads; prompt 2 builds the process shape; prompt 3 adds the two out-of-band channels; prompt 4 is the lifecycle surface and needs all three because `status` reports the metrics state the supervisor writes; prompt 5 is the integration assertion that no single prompt can make on its own.

## Alternatives Considered

- **Keep twelve plists and just point them at the Go binary.** Rejected: that keeps the twelve-way drift this change exists to remove, and every settings change stays a twelve-place edit.
- **Read settings from environment variables in the plist.** Rejected: launchd plists are world-readable, so that puts the pushgateway password in twelve world-readable files — the current state, and the reason for the config file.
- **`PUT` the metrics like the Python tool originally did.** Rejected: `PUT` replaces the whole grouping-key group, so the heartbeat erases last-success every cycle and the stall alert can never fire. The Python tool moved to `POST` for exactly this reason.
- **One launchd agent per vault, all running `supervise --config`.** Rejected: twelve agents racing on the same config is the same multiplier with a different name.
- **Reimplement the sync loop inside `supervise`.** Rejected: the quiet-window, conflict and lock behaviour is the part most likely to drift; calling `internal/watch` keeps one implementation.
- **Make the config file mandatory for every subcommand.** Rejected: it would break `watch`, `sync` and `resolve` on a machine with no config file, which is a regression of three shipped commands and defeats the Python/Go coexistence window.
- **One state file per vault.** Rejected: `status` would then need a directory walk to answer "what is the freshest push", and the per-vault files would drift the same way the plists did. One file, one serialised writer.
- **Add a `--dry-run` to `install`.** Not now: the plist is a file, and the test seam already renders it without loading it. A dry-run flag would be a second code path to keep correct.

## Do-Nothing Option

The twelve Python watchers keep running. The Go binary stays a per-repository tool, the twelve plists keep drifting, the pushgateway password stays in ten world-readable files, and the memory multiplier the goal exists to remove stays in place. The cutover task cannot start, because there is no supervisor to cut over to.
