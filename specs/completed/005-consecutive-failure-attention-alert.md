## Summary

- `git-ai-sync watch` retries a failing sync forever and tells nobody: a commit the pre-commit hook keeps refusing because a staged path is unsafe on Windows stalled one vault for ~12.5 h (1,194 consecutive failures) and left its checkout 680 commits behind, while every liveness check passed.
- Add a consecutive-failure counter to the watch loop: when a cycle fails and the loop continues, the counter increments; when a cycle succeeds, it resets to 0; a debounce-skip cycle leaves it unchanged.
- At the configured threshold (default 10 consecutive failures, ~5 min at the default 30 s cadence) post **exactly one** card to the operator's attention board, naming what stalled and what is blocked; do not post again until the counter is reset.
- On the next successful cycle, reset the counter and close the card (clearing the outstanding guard regardless of the close's outcome).
- The notifier is a best-effort side channel like the existing pushgateway push: a missing script, a non-zero exit, a timeout, or an unreachable store is logged at WARNING and never fails or stalls a sync cycle.

## Problem

`git-ai-sync watch` runs as a per-vault launchd (macOS) / systemd (Linux) service. When a sync cycle fails in a way the loop can continue past — a commit the pre-commit hook refuses because a staged path is unsafe on Windows (the class behind the observed incident), an unreachable remote, a failing push — the loop logs the failure and retries on the next interval, forever. Nothing distinguishes "one transient blip" from "this vault has not landed a commit in twelve hours": the process is alive, launchd reports it healthy, the log grows, and no one is told. What each class costs today differs. The pre-commit hook has two refusal classes: the unsafe-path refusal (a staged name illegal on Windows) is caught and the loop continues, so it is a looping failure, while the marker refusal (staged content containing conflict markers) exits the process and is out of scope here. Since spec 004 (PR #18) the unsafe-path class no longer skips the pull — the refusal is logged as `Commit refused; pulling anyway: ...` and the checkout keeps tracking the remote — but the commit is still refused every cycle, so the vault's local edits never land, and nothing signals that. The pull-failure classes (an unreachable remote, a failing push) still log `Sync failed: ... Continuing to watch...` and drift further behind the remote on every retried cycle. The observed ~12 h stall was the unsafe-path class. The sibling metric spec (002) added an age-of-last-success alert for the *stopped* case, but that alert lives in the cluster and fires on the pushgateway's own window; a machine-local, immediate, human-readable card on the operator's board for the *looping* case does not exist. The observed cost is a vault that "felt stale" to a human hours after it broke.

## Goal

A vault whose watch loop has failed N consecutive cycles raises exactly one operator-facing card on the attention board naming the vault, the failure count, and the last error, and closes it automatically as soon as a cycle succeeds — while a single isolated failure stays silent. Detection happens on the machine running the watch process, within about N × interval of the first failure, and never depends on the cluster, the pushgateway, or a Claude Code session being open.

## Non-goals

- No auto-recovery of the stall — this spec only notices and notifies. The shipped unsafe-path recovery (spec 004) and the existing `git-ai-sync resolve` remain the recovery paths.
- No coverage of failures that make the watch process **exit** — the marker-refusal path added by spec 002 (staged content containing conflict markers) and the pull-conflict path, both `sys.exit(1)`. Those cycles never reach the counter, and their launchd restart resets it; they are already loud (non-zero exit plus an explicit log line) and covering them would require a persisted counter — a separate spec. See Failure Modes.
- No re-post when the outstanding card is answered by the operator or expires while the vault is still stalled. The guard is in-memory and still holds the old item id, so no second card is posted until a cycle succeeds and clears it. Detecting that the operator already answered would require polling the store, which this spec does not do; the stall simply waits for recovery.
- No persisted counter, and no state file on disk. The counter is per watch-process; the store's open-scoped dedup key is the durable guard.
- No change to `cmd_sync` (one-shot), `cmd_resolve`, `cmd_status`, or `cmd_doctor` — the counter and notifier exist in `watch` mode only.
- No change to the pushgateway metrics path (spec 002) or its series.
- No general-purpose alerting framework, no per-vault alert routing, no notification channels other than the attention board.
- No authentication for the attention store — the local default (`http://localhost:18080`) is unauthenticated, exactly as the posting script itself assumes. A token-protected store is out of scope.
- No second notifier mechanism: the card is posted by the supervisor's `attention-ask.py` script (hard requirement); git-ai-sync does not re-implement the ask protocol.
- Do NOT add an enable/disable flag for the notifier — a missing script path is the disable path, and an escape hatch on the Goal is itself a regression.
- Do NOT make the dedup key, the vault label, or the producer id configurable — the key format is the store's re-post suppression contract.
- Do NOT add a persisted failure counter — in-memory is the invariant here; a crash-loop-capable counter is a separate spec.

## Assumptions

- The supervisor plugin is installed on the machines that run the vault watchers, at a path reachable from the watch process. It is *not* assumed present: the notifier degrades to a startup WARNING when the script is absent.
- The attention store is reachable at the URL the posting script uses, and the store is new enough to accept the card (the `owner:` liveness model and `expires_at` enforcement). An older store rejects the push; that is a store-version issue, not a notifier bug.
- The store treats an illegal close transition as an error, not a no-op: it rejects a repeat close of an already-closed item with HTTP 409 rather than reporting success.
- Exactly one watcher runs per vault (the existing deployment contract from spec 002).
- The dedup key `git-ai-sync-<vault>-stalled` is unique per vault and stable across process restarts.

No criterion requires the real vault, the cluster, or a *live* attention store: the post is observed through the argv-recording stub, and the close through the recording HTTP endpoint.

## Desired Behavior

1. `watch` mode classifies each loop iteration (a cycle) into exactly one of three outcomes and updates the consecutive-failure counter accordingly. Classification is **per cycle, not per phase**: the cycle's phases (commit, pull, push) may fail independently, and a cycle in which the commit failed while the pull and push succeeded is still a single failure.
   - **failure** — a phase of the cycle raised an exception that the loop caught and continued past, and the loop then started its next iteration: increment the counter by 1 (once per cycle, however many phases failed). This covers the caught `GitError` handlers and the unexpected-`Exception` handlers in every phase, including the unsafe-path refusal (caught, logged, and fallen through to the pull).
   - **success** — every phase of the cycle ran to completion without a caught-and-continued exception, including the idle "No local changes" cycles and the ahead-of-remote push cycles: reset the counter to 0.
   - **skip** — the debounce gate suppressed the cycle ("Skipping - files changed"): leave the counter and any outstanding card unchanged. A skip is neither a failure nor a recovery.
   Classification keys on whether the loop continued, not on the exception class: `MarkerRefusalError` and `UnsafePathRefusalError` are both `GitError` subclasses, but a marker refusal ends the process (neither of the three) while an unsafe-path refusal is caught and continued (a failure). A cycle that ends the process — `sys.exit` after a marker refusal or a pull conflict, or an uncaught exception — is none of the three and never updates the counter.
2. When the counter reaches the configured threshold N (default 10, minimum 2) and no card is currently outstanding, git-ai-sync posts **exactly one** attention-board card. It does not post again while that card is outstanding, and it does not post again after the counter is reset until a new run of N consecutive failures occurs. The outstanding guard is in-memory only: if the operator answers the card, or the card expires, while the vault is still stalled, the guard still holds the old item id and no new card is posted until a cycle succeeds (see Non-goals).
3. The "card is outstanding" guard is the item id returned by a *successful* post. A post that fails (store unreachable, script missing, non-zero exit, unparseable output) does not set the guard, so the next failing cycle retries the post; the store's open-scoped dedup key is the second line of defence against a duplicate if a post succeeded but its item id could not be read. The guard is cleared on the first successful cycle **regardless of the close's outcome**: a failed close leaves the card on the board (until the operator answers it or it expires) but must not leave the guard set, or every later card for the rest of the stall would be silently suppressed.
4. The card is posted by invoking the supervisor's attention-ask script with: the dedup key `git-ai-sync-<vault>-stalled`; an explicit producer id `git-ai-sync-<vault>`; producer kind `cron`; the script's default owner liveness ref (no `--liveness-ref` override); the script's default expiry (no `--expires-at` override); a `--payload` naming what stalled (the vault label and the failure count); a `--context` naming what is blocked (the repository path, the time of the first failure in the run, and the last error summary truncated to at most 200 characters); and exactly two `--option` labels with `--recommend` naming the actionable one. The vault label is the repository directory name, reusing the same label the pushgateway series already uses, so one vault has one label across both surfaces.
5. On the next successful cycle, the counter resets to 0 and, if a card is outstanding, git-ai-sync closes it by `POST`ing to the attention store's close route for that item id. The close is best-effort and is never retried: if it fails, or the store rejects it as an illegal transition (HTTP 409 because the card was already closed), the card remains until the operator answers it or it expires, and both the counter and the guard are cleared regardless. Closing releases the dedup key, so a *later* stall posts a new card.
6. Every notifier interaction is best-effort and bounded: a missing or non-executable script, a non-zero exit, a subprocess timeout, unreadable output, an unreachable store, or a rejected close is logged at WARNING and never raises, retries within the cycle, or otherwise changes the cycle's outcome or timing. The notifier subprocess timeout and the close-request timeout are both `metrics.PUSH_TIMEOUT_SECONDS` (5 seconds) — the same bound the pushgateway push already uses.
7. When the notifier script is absent, the notifier is disabled: a single startup WARNING names the missing path (mirroring the pushgateway-disabled WARNING), zero notifier attempts are made per cycle, and the sync loop behaves exactly as it does today.
8. The notifier script path (`GIT_AI_SYNC_ATTENTION_SCRIPT`), the attention store URL (`ATTENTION_STORE_URL`, which carries no `GIT_AI_SYNC_` prefix), and the failure threshold (`GIT_AI_SYNC_STALL_THRESHOLD`) are configurable; the defaults are `~/.claude/plugins/marketplaces/claude-supervisor/scripts/attention-ask.py` (the supervisor plugin's script, resolved from `Path.home()` at runtime rather than pinned to the version-numbered plugin cache path, which changes on every plugin update), `http://localhost:18080` (the same default the posting script itself uses), and 10. The threshold stays configurable because the watch cadence varies per vault: the default 10 detects in ~5 minutes at the 30 s launchd cadence, but a vault on a 5-minute interval needs N = 3 to keep detection under ~15 minutes. The threshold must be ≥ 2 — a value of 1 would post on a single failure and violate the isolated-failure rule. That check is applied when `watch` starts, not when the configuration is constructed, so `sync`, `status`, and `doctor` are unaffected by a threshold value they never read. `setup-launchd` threads all three settings through to the installed agent, exactly as it already threads the pushgateway settings, so a launchd-managed vault can set them.

## Constraints

- Python 3.14, `uv`, ruff, mypy **strict**, pytest with `asyncio_mode = "auto"`; `make precommit` stays green (ruff strict, mypy strict, pytest).
- The notifier must follow the `metrics.py` precedent exactly: a stateless module of functions that return a bool, never raise, and log every failure at WARNING. It must be safe to call from inside the watch loop with no try/except around it.
- The counter is stateful, so it may be a small object in the `ChangeTracker` style (a class holding one integer); the notifier itself stays functions-over-classes, per the existing pattern.
- Invoke the notifier as an argument vector, never through a shell — no `shell=True`, no string interpolation into a command line. The script path comes from configuration, so it is validated as a regular, **readable** file before use, and invoked as `[sys.executable, str(script_path), "post", …]`. **Never gate on the executable bit.** The supervisor's `attention-ask.py` ships mode **100644** in every installed copy — measured 2026-10-11: the marketplace copy, its git mode (`git ls-files -s` → `100644`), and all **188** plugin-cache copies — and every caller in the plugin runs it as `python3 attention-ask.py`. An `os.access(..., os.X_OK)` gate therefore returns `None` on every machine, silently disabling the notifier in production while every stub-based test still passes (the stub is `chmod 0o755`).
- The close request must validate the item id as a 32-character hex store id before it is placed in the URL path; an item id that does not match is treated as unreadable (WARNING, no close attempt) rather than interpolated.
- Never place a credential, a token, or a remote URL (which can carry embedded credentials) into the payload or context. Carry only the error summary text and the repository path; the pre-existing "never log credentials" rule applies to the card as it does to the log. The error summary placed in the card's context is truncated to at most 200 characters.
- The notifier's argv and the card's wording must not include the pushgateway URL, the model name, or any environment value — only the vault label, the count, the repository path, and the last error summary.
- No absolute paths hardcoded in source; the default script path is resolved from the home directory at runtime (`Path.home()`), never written as a literal user path.
- The producer id must be passed explicitly, never left to the script's default: the posting script refuses to post when neither `--producer-id` nor `CLAUDE_CODE_SESSION_ID` is set, and a launchd-spawned watch process has no `CLAUDE_CODE_SESSION_ID`. The script's exit code is the post verdict — 0 means the card was created and its item id is on stdout as `ITEM_ID: <id>`; any non-zero exit means no card exists.
- The close route is `POST {store}/api/1.0/attention/{item_id}/close` on the same store the post used; it is a producer withdrawing its own item and needs no body and no credential against the local default store. The posting script exposes no close verb, so the close is issued directly against the store route. The store contract the notifier depends on — the close route, the `ITEM_ID: <32-hex>` stdout shape, the posting-script flags, and the `owner:` liveness / `expires_at` model — is documented in `docs/attention-store.md`.
- The store rejects an illegal transition rather than treating it as a no-op: a repeat close of an already-closed item returns HTTP 409, so the close is never retried and a 409 never leaves the guard set.
- The new configuration fields live in the existing pydantic settings model and are prefixed `GIT_AI_SYNC_`, except the attention store URL, which must resolve the same environment variable the posting script itself reads (`ATTENTION_STORE_URL`, default `http://localhost:18080`) so that the post and the close can never disagree about which store they are talking to.
- The counter and the notifier must not run in `cmd_sync`; one-shot sync keeps today's exit-non-zero-on-failure behavior unchanged.
- The existing pushgateway behavior, metric names, and their per-vault grouping key are unchanged.
- Existing tests must still pass; the watch-loop tests that patch `time.sleep` with a side-effect list keep working (the new logic runs inside the loop body, not around `sleep`).

## Security / Abuse Cases

- **What an attacker can control.** The contents of the watched repository: file names, commit messages, and remote URLs all reach the error text that becomes the card's context. The error summary placed on the card must therefore be treated as untrusted: it is passed as a single argv element (never a shell string), it is truncated to at most 200 characters, and remote URLs — which can embed a token — must never be included. Only the vault label, the count, the repository path, and the error summary cross to the board.
- **Trust boundary.** git-ai-sync shells out to a configured script path and issues an HTTP POST to a configured store URL. Both are configuration, not user input, but both are validated: the script must be a regular readable file (see the argv constraint above — not the executable bit), and the item id must match the 32-hex store-id shape before it is used in the close URL, so a crafted or truncated value cannot redirect the close.
- **Credential leakage.** The card is durable and operator-visible, so it is a leak surface like a log file. No environment value, credential, pushgateway URL, or remote URL may appear in the argv or the payload; the same "never print a secret" rule that governs the log governs the card.
- **What can hang or retry forever.** The notifier subprocess is bounded by a timeout and is never retried within a cycle; the close is a single bounded request that is never retried even when the store rejects it. Neither can block the watch loop beyond the timeout, and neither retries in a way that could storm the store.
- **What must be validated.** The threshold (≥ 2, checked when `watch` starts), the script path (exists, executable), the store URL (a parseable http/https URL), and the item id (32 hex) are all validated; an invalid value disables the notifier with a WARNING rather than raising.

## Suggested Decomposition

This spec touches four concerns (a stateful tracker, a notifier module, the watch-loop wiring, and the launchd/config plumbing) with 8 Desired Behaviors and 15 Acceptance Criteria, so the work splits into prompts in dependency order.

| # | Prompt focus | Covers DBs | Covers ACs | Depends on |
|---|---|---|---|---|
| 1 | `notifier.py`: the consecutive-failure tracker + the attention-ask post (argv build, subprocess with timeout, `ITEM_ID:` parse, best-effort) + the store close (direct POST, 32-hex id guard, no retry) + unit tests with a stub script and a recording stub HTTP endpoint | 1, 3, 4, 5, 6, 7 | 7, 8, 10 | — |
| 2 | `config.py`: the threshold (≥ 2), the script path, and the store URL fields, plus their unit tests | 8 | 12 | — |
| 3 | `__main__.py`: wire the tracker and the notifier into `cmd_watch`, classifying each cycle as failure / success / skip, plus the loop-level unit tests and the throwaway-clone integration run | 1, 2 | 2, 3, 4, 5, 6, 9, 10, 11 | prompts 1, 2 |
| 4 | `launchd.py`: thread the new settings through `setup-launchd`'s env passthrough + its test | 8 | 13 | prompt 2 |
| 5 | `README.md`, `docs/launchd-service.md`, and `docs/attention-store.md`: the environment-variable table, the stall-alert section, the extended plist passthrough list, and the store contract | — | 14, 15 | prompts 2, 3 |

Rationale: prompt 1 establishes the notifier contract and the tracker's semantics in isolation, so prompt 3 only has to decide *when* to call them. Prompt 2 must land before 3 because the loop reads the threshold. Prompt 4 is independent plumbing once the field names exist. Prompt 5 is documentation and depends on the field names and the loop behaviour being settled. Prompt 3 carries the integration run (AC 11) and the second-stall AC (AC 9) because it owns the loop. AC 10 straddles prompts 1 and 3 by design: its (b) sub-case (a failing or hanging stub) is notifier-level and lands with prompt 1, while its (a) sub-case (a watch run with the script path absent) is loop-level and lands with prompt 3 — each prompt owns its half, so both rows list it. AC 1 (`make precommit`) is the shared gate across all prompts.

## Do-Nothing Option

The history this spec exists for is the incident that produced spec 004: a vault whose every cycle was refused ran ~12.5 hours (1,194 consecutive failures) and left the checkout 680 commits behind while a human noticed only by accident. Spec 004 (PR #18) closed the checkout-drift half of that for the unsafe-path class — the pull now always runs — but it added no signal: the refusal is logged only locally, the vault's local edits still never land, and a pull-failure class (an unreachable remote, a failing push) still loops and drifts behind with nothing but `Sync failed` in the log. The pushgateway age-of-last-success alert (spec 002) covers the cluster side but fires on its own window and needs the pushgateway reachable; it gives no immediate, machine-local, human-readable card. Cost of doing nothing: the next looping failure runs for hours with its only evidence a log line nobody reads, and every tool reading the vault answers from a snapshot nobody knows is stale.
